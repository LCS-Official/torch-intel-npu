# Decode KV 更新对照：保留默认 Select

2026-10-07，Core Ultra 7 258V / Lunar Lake NPU40xx，驱动 32.0.100.5540，
编译器 8.3，Torch 2.14.1+cpu，沿用 `.conda/npunlock`。

本轮完成三种可执行 KV 更新候选及一个编译失败候选的隔离检查。
Gather 在四层校准 W8、B4 decode 下两轮测得约 8% / 12% 的中位耗时下降，
但 B1 出现回退，B4 FP16 的逐轮结果也不稳定。因此未接入默认模型。
上一轮已接入的 SHAVE RMSNorm 优化继续生效，默认源码、ELF、runtime 和接口指纹均未改变。

## 候选与实测

原路径对 K / V 分别做广播 Select，把新 token 写入 64 槽 KV 的指定位置。
候选保留独立输出和旧快照所有权，不对旧 KV 原地写入：

- `gather`：把旧 64 槽和新 token Concat 为 65 槽，通过 64 个索引选择结果。
  指定位置读第 65 槽，其他位置读对应旧槽。索引为 INT64。
- `gather_i32`：相同更新方式，改用 INT32 索引。
- `scatter_flat`：把 KV 展成 `(B*3*64,64)`，使用 ScatterUpdate 一次更新
  `B*3` 个连续行，随后恢复形状。索引计算涉及的整数不超过 1535，FP16 可精确表达。
- `scatter_nd`：相同扁平行索引，改用 ScatterNDUpdate。此候选 decode 图被当前
  驱动编译器拒绝：`ir2blob.compile` / Level Zero `0x78000007`，没有该图的性能结果。
  这只说明本次 IR 组合未编译成功，不能据此断言硬件不支持所有 ScatterND 用法。

测试真实 SmolLM2-135M embedding 和前四层，FP16 / 激活校准 W8A16，
B1 prefix 32 / B4 prefix 16。W8 权重来自上一轮的 `calibrated-current`，
严格校验源码和权重指纹，没有重新量化或放宽精度门槛。

每组预热后做 31 轮 ABBA / BAAB 对照，每个版本 62 个样本；
计时包括 Torch 调用、提交与同步，结果清理和诊断下载在计时外。
下表为“旧 Select → Gather”中位耗时，单位 ms：

| 配置 | 进程 0 | 耗时下降 | 胜出轮数 | 独立确认进程 | 耗时下降 | 胜出轮数 |
|---|---:|---:|---:|---:|---:|---:|
| B1 FP16 | 2.83735 → 2.84190 | -0.16% | 9 / 31 | 3.43695 → 3.55885 | -3.55% | 10 / 31 |
| B1 校准 W8 | 2.95780 → 3.01870 | -2.06% | 16 / 31 | 2.90705 → 3.15675 | -8.59% | 13 / 31 |
| B4 FP16 | 3.03905 → 2.92575 | 3.73% | 21 / 31 | 3.03565 → 2.89145 | 4.75% | 16 / 31 |
| B4 校准 W8 | 3.12420 → 2.87425 | 8.00% | 25 / 31 | 4.10725 → 3.61585 | 11.96% | 20 / 31 |

负数表示变慢。逐轮配对下降中位数也已保存：B4 FP16 为 2.78% / 0.79%，
B4 校准 W8 为 8.68% / 12.01%。因此不能把 B4 FP16 两个版本的中位数差
当作同样稳定的逐次收益，更不能把 B4 结果外推给 B1。

其他候选仅做一轮筛选，以下为中位耗时下降百分比：

| 候选 | B1 FP16 | B1 校准 W8 | B4 FP16 | B4 校准 W8 |
|---|---:|---:|---:|---:|
| INT32 Gather | -0.55% | -6.81% | -4.06% | 9.64% |
| 扁平 ScatterUpdate | -1.77% | 0.95% | 6.23% | 11.22% |

两者都没有证明普遍优于默认路径，B4 校准 W8 也都仅胜出 19 / 31 轮。
本轮不增加按特定模型、batch 和精度选择候选的默认分支。
所有暖计时段驱动分配为零，没有显式主机载荷复制或新图编译。
桌面负载、温度和频率未控制，各进程绝对耗时不宜直接比较。

## 设备任务核对

复用已有隔离 profiling DLL，对 B4 校准 W8 的 Select / Gather 各采三份设备任务。
profiling 图与普通图输出逐位一致，但 profiling 会改变执行成本；
下表只用于解释任务结构，不代替上面的正常路径交错计时。
四层各自区间求并集后相加，单位 ms：

| Decode 指标 | 默认 Select | Gather 候选 |
|---|---:|---:|
| 已记录设备跨度 | 2.35131 | 2.18460 |
| SHAVE 活跃时间 | 1.85325 | 1.58783 |
| Select 活跃时间 | 0.57249 | 0.14771 |
| Gather 活跃时间 | 0.02708 | 0.23035 |
| RMSNorm 活跃时间 | 0.70708 | 0.69682 |
| DPU 活跃时间 | 0.13487 | 0.12433 |
| 四层 SHAVE 任务数 | 424 | 480 |

Select 任务从 80 减至 32，Gather 任务从 8 增至 112，每层总 SHAVE 任务增加 14 个。
这说明减少 Select 的工作确实有潜力，同时替代图引入了更多 Gather 和任务调度。
结合图中的额外 Concat，可推断布局与搬运成本抵消了部分收益；
本平台没有 DMA profiling，无法单独量化搬运成本，也不能把记录空档全部归为 IO。
任务时间线保存在两个 `device-*` 目录的 `*-trace.json`。

## 正确性与复核

- 四个成功进程各 172 项四层检查，均通过：prefill、单步 decode、连续位置推进、
  同一旧 seed 重复 decode。B1 连续 32 步，B4 连续 48 步，最后 cache 长度为 64。
  旧 prefill 输出和 seed KV 保持不变。
- 候选与默认路径共核对 8,944 项输出 / KV / 位置数组，全部逐位一致；
  另核对 6,708 项跨进程 baseline 数组及 102 项 profiling 数组。
- 共 14,496 次成功 NPU 调用；144 张保存的图、48 份新鲜任务采样、
  7,224 条 task 记录通过原始二进制和指纹复核。
- 成功进程关闭后 live / cache / quarantine 缓冲归零，上下文没有失败。
  编译拒绝的 ND 实验单独保存，不计入成功调用和性能统计。
- 最初测试脚本的一处局部变量清理错误已修正，原源码、日志和失败记录保存在
  `initial-cleanup-error/`，不用于性能结论。没有修改正式模型或数值容差。

`measurement-v1.py` 是首轮 Gather / ND 测量源码；当前研究脚本增加了两个筛选候选。
`sources/` 保存当前源码和二进制快照，`before/torch_npu_smollm.py` 与当前默认模型相同。
`audit.json` 从原始 NPZ、图、task 二进制及逐轮样本重算以上结论。

在 `E:/Pytorch_xfire_NGPU` 中离线复核：

```powershell
.\run_torch_npu.ps1 -Script .\npunlock-probe\research\kv_gather_audit.py
```

重新采样时使用新 label，避免覆盖原始数据，例如：

```powershell
.\run_torch_npu.ps1 -Script .\npunlock-probe\research\kv_gather_probe.py -ScriptArguments '--candidate','gather','--label','repro'
```

或验证更直接的 SHAVE 连续行复制内核；单纯继续替换高层算子尚不足以形成通用加速。
