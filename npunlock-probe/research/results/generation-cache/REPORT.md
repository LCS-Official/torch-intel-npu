# 完整生成的分配缓存诊断与修复

2026-10-10，Lunar Lake / Ultra 7 258V，NPU 8086:643e，驱动 32.0.100.5540。
PyTorch 2.14.1+cpu，现有 npunlock 原生后端，不依赖 OpenVINO。

已将默认空闲缓冲区数量上限由 128 改为 256，并重建正式扩展。
已测 SmolLM2-135M-Instruct、30 层、B1、24-token 提示词、生成 32 token 的预热流程，
驱动分配从每次 86 次降为 0；FP16 / W8A16 完整生成计时中位数均降低约 1.2%。
全部 32 步 logits / token 新旧逐位一致，正式设备和轻量训练回归通过。

## 原因与最小修改

分配器已有按字节数精确匹配的空闲块复用，同时限制块数和总字节数，超过上限时淘汰最早释放的块。
原 128 块上限容不下这个生成流程所需的 214 块：每轮结束淘汰 86 块，下一轮又向驱动申请。
追踪到的淘汰全部由块数上限触发，没有一次由 16 MiB 字节上限触发。

| 空闲块上限 | 每轮驱动分配 / 淘汰 | 生成状态清理后缓存块数 | 缓存字节数 |
| --- | ---: | ---: | ---: |
| 128 | 86 / 86 | 128 | 2,066,856 |
| 192 | 22 / 22 | 192 | 2,963,184 |
| 256 | 0 / 0 | 214 | 3,068,016 |

128 块版本的 86 次申请位于：prefill 输入上传 1 次、prefill decoder 2 次、
第一次 decode 的 decoder 65 次、第二次 decode 的 decoder 18 次；后续 29 步已没有申请。
对应尺寸为 3 × 27,648 B、29 × 1,152 B、36 × 24,576 B、18 × 4 B。
192 块仍有 22 次申请，因此采用常量 256，给已观测的 214 块留出余量。

正式源码只改两处常量：`backend.cpp` 的 `max_cached_buffers`，以及
`torch_intel_npu.stats()` 对应的 `allocation_cache_limit_blocks`。
16 MiB 字节上限、精确尺寸复用、淘汰顺序、生命周期、失败隔离和 shutdown 逻辑均保留。
模型图、原生 session DLL、SHAVE 内核、计算精度和量化方式没有改变，无用户开关或新增依赖。

这个工作负载多保留 1,001,160 B（约 0.955 MiB）空闲缓存；不是新增同等规模的常驻模型参数。
生成状态清理后仍存活的 181 块 / 1,866,244 B 属于模型归一化参数与标量等持久状态；
模型销毁并 shutdown 后，正常运行的 live / cached / quarantined 字节数均为零。

## 配对性能

隔离诊断扩展在同一个进程内切换 128 / 256 块，复用同一组 60 个已编译模型图。
两种策略均使用默认 group4。每次切换会清空空闲缓存，并先完整生成两次，预热不计时。
每个精度 7 轮交替 ABBA / BAAB，共 28 个计时样本，每种策略各 14 个；计时阶段关闭事件追踪。

| 模式 | 原 128 块耗时中位数 | 256 块耗时中位数 | 耗时降低 | 吞吐量（32 / 中位耗时） | 256 更快的轮数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| FP16 | 490.749 ms | 484.910 ms | 1.190% | 65.21 → 65.99 token/s | 7 / 7 |
| W8A16 | 452.282 ms | 446.944 ms | 1.180% | 70.75 → 71.60 token/s | 5 / 7 |

首 token 中位耗时：FP16 24.207 → 23.165 ms，W8A16 23.238 → 22.976 ms。
每个 128 块样本均申请 86 次，每个 256 块样本均申请 0 次。
每次完整预热生成 NPU 调用 960 次、chain 图 930 个、chain 分组 248 个，新增 session 为 0，
显式 host upload / download 各 32 次；这些计数新旧相同。

计时覆盖 32-token 循环内的 CPU embedding / 最终 norm / head / argmax、上传下载和 NPU decoder。
最终生成状态销毁、KV 验证和结果比对在计时之外，因此不是包含所有收尾工作的请求服务延迟。
桌面后台负载、频率未锁定，约 1.2% 是本组配对中位数变化，不能保证任意场景相同收益，
也不与前几轮独立实验的速度增益相加。事件追踪样本只定位分配，未混入性能统计。

## 数值、正式接入与保护检查

- 128 / 192 / 256 的全部 32 步 logits / token 逐位一致；最终 30 层的 K / V / position 共 90 个数组逐位一致。
- FP16 / W8A16 配对样本均逐步比对 32 行 logits 和 token，并通过原有有限值检查。
- 标准构建脚本重建正式 `_torch_intel_npu.pyd`，没有引入诊断接口。
  正式版本各精度另外执行 8 次计时确认，均 0 次预热驱动分配，全部 32 步输出与隔离基线逐位一致。
  该确认复用了原 runner 的两种标签，两者实际都为 256 块 / 默认 group4；不能作为第二组 128 对 256 性能实验。
- 5 项 allocator guards：精确复用、最后一个 storage view 的生命周期与 empty_cache、块数 / 字节上限、4 线程复用、持有 storage 时 shutdown。
- 3 项空闲释放顺序检查通过。
- 合成失败隔离检查通过：没有实际设备提交，没有驱动 free / reset，失败缓冲区留在 quarantine。
  这个专用失败 fixture 的 context_failed / quarantine 非零属于预期，与正常清理检查分别断言。
- 33 项正式设备检查通过。
- 11 项快速训练 / 梯度 / 契约检查通过，含 FP16 / FP32 的 MLP、卷积、小型 ResNet 各 3 步。
  本次这些训练样本不逐步重置 CPU 参考。长期训练、BatchNorm 网络与既有 FP16 长轨迹限制未重新认证。
- 正式文件快照、构建指纹、全部冻结输出及上述回归的最终离线审计通过。

本轮没有放宽精度门槛。FP16 首步 logits 相对 CPU FP16 的 L2 误差约 0.484%；
W8A16 仍约 5.69%，超过既有 3% 量化质量门槛。
新旧逐位一致意味着分配修复没有改变输出，不等于 W8A16 模型质量通过。
零分配只覆盖这里的预热配置；冷启动、新尺寸、其他模型或字节预算触顶时仍可正常申请 / 淘汰。

## 证据与复核

`trace-fp16.json` 保存各阶段的分配、复用与淘汰原因；`benchmark-*.json` 保存全部样本。
对应 `*-outputs.npz` 保存 logits / token，以及 trace 的 90 个最终 KV / position 数组。
`production/` 为正式扩展的确认，`checks/` 为保护、设备和训练回归及日志。
`before/`、`after/`、`promotion.json` 保存正式修改前后文件与指纹；诊断扩展在独立的 `diagnostic/`。
只保存小型输出、图指纹和所需扩展，没有再次复制模型权重或完整编译图集合。
