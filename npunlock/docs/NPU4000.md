# Experimental Lunar Lake / NPU4000 FP16 and FP32

Verified local profile: Core Ultra 7 258V, NPU 8086:643e, driver
32.0.100.5540, graph compiler 8.3. The packaged native DLL is unchanged.
Generic custom-C compilation/discovery remains on the NPU3720 path.
This Python module uses precompiled 4000xx ELF kernels and validated patching.

## Elementwise API

```python
from pathlib import Path
import numpy as np
from npunlock.npu4000 import compile_unary, compile_binary

root = Path("tests/fixtures/npu4000/precision")
x = np.array([[70000., 1.000244140625, 2**-140]], dtype=np.float32)
p = compile_unary(x.shape, (root / "add1-f32.elf").read_bytes(), dtype="f32")
y = p.run({"x": x})["y"]
q = compile_binary(x.shape, (root / "mul-f32.elf").read_bytes(), dtype="f32")
z = q.run({"x": x, "b": np.ones_like(x)})["y"]
```

compile_unary uses a verified Abs carrier. compile_binary uses Power and
three MemRefs: x, b, y. Inputs match shape and dtype; kernel arithmetic replaces
the carrier operation. Source must match the declared ABI. Broadcasting belongs
to the workspace Torch adapter. Use native_dir or NPUNLOCK_NATIVE_DIR for DLLs.

## Precision and cast transport

compile_precision_graph requests EXECUTION_MODE_HINT="ACCURACY" and
DisablePrecisionConversion. Pure FP32 graphs must have SHAVE tasks,
FP32 MemRefs and no DPU tasks. Ordinary driver FP32 MatMul fails this check;
the Torch adapter uses custom SHAVE multiply and pairwise add instead.

compile_cast(shape, dtype=..., kernel_elf=...) is a physical transport API:

- f16->f32 patches Convert with IEEE binary16 decoding; Program output is FP32.
- f32->f16 uses an FP32 Abs carrier with SHAVE rounding/encoding.
  Output bytes contain binary16 codes in the low 16 bits of uint32 lanes.
  Decode those bits as FP16, never numerically convert carrier floats.
  The Torch adapter performs that storage unpacking.

Tested hardware conversion and arithmetic paths flush subnormals.
arithmetic.c handles these edges with SHAVE integer operations and nearest-even
rounding; normal arithmetic remains SAU.f32. NaN payload preservation and
CPU-identical reduction ordering are not promised.

## Patch contract

- Exact vendor/device 8086:643e and compiler 8.3.
- Static f16/f32, 1–4 positive dimensions, <=65,536 host elements.
- Dense matching CMX layouts; Convert separately validates input/output widths.
- One shared window matching the original Abs, Power or Convert SHA-256.
- Linked little-endian SHAVE ELF32 for 4000xx, entry 0x1d000000.
- Text fits the window; no extra allocated data or unresolved relocations.

Validation covers 40-byte ranges, 96-byte invocations, 40-byte MemRefs, tile
references, strides, dtype, CMX bounds and disjoint output buffers.
Only kernel text changes; ELF size, DMA, barriers, tasks and relocations stay intact.
Unknown profiles/layouts fail closed. Source, ELF and assembly hashes are in
tests/fixtures/npu4000/precision/manifest.json. Build with the workspace research
script through the isolated Movi worker, target 4000xx, -O2 -ffp-contract=off.

## Reusable execution context

graphinfer_session_create_child loads another graph into the parent's Level Zero
context. Buffers from that context can bind to any sibling graph with matching
argument byte sizes; unrelated contexts, wrong sizes and output/input aliases
are rejected. Children and buffers retain the context after their parent graph
closes. CPU and native context locks serialize execution and release; each
submission waits for its fence before the next graph uses the output.
One command queue is retained for the context's lifetime. Native ELF backing is
owned until graph destruction (also retained in Python for older DLLs).
The locally rebuilt session DLL also retains one command list and fence per
graph. Each call rebinds the validated current tensors and records fresh commands;
after its completion fence succeeds, the list is cleared and the fence reset.
No tensor addresses or allocations are cached across calls. Graph close releases
these objects before graph destruction; uncertain completion preserves them in
the quarantined context. This keeps dynamic output allocation and sibling graph
bindings safe without a pointer-keyed replay cache.
Repeated threaded checks reproduced device-lost before image-lifetime changes;
queue persistence alone and a dedicated submission thread did not eliminate it.
After retaining the image, three consecutive full checks passed, including 2000
serialized threaded submissions each, without the dedicated-thread workaround.
This is observed behavior, not a complete explanation of Windows driver internals.

The Python equivalent is NativeLibraries.create_inference_session(blob,
parent=other_session). NativeLibraries(session_library=...) optionally loads
the locally rebuilt inference-only DLL while retaining the release compiler
and workers. Older DLLs remain usable for single sessions but reject child
session creation explicitly. Public result/buffer structure layouts are unchanged.

The workspace torch_npu_runtime.py provides fixed-shape FP16/FP32 resident
buffers, explicit upload/download and the basic unary/binary kernels. It is
not a Tensor device allocator yet. Hardware checks include 1000 recursive
add/multiply rounds per precision without intermediate host payload copies or
new payload allocations, 2048/65536-element Abs, parent/child lifetimes,
input changes, repeated teardown and serialized threaded submissions.
DMA and CMX carrier tasks are retained; GPU pointer interoperability and large
memory-budget changes are not tested.

Queue submission/fence errors quarantine the context: no further inference,
device free, graph destruction or driver unload while completion is uncertain.
Resources remain until process exit. The native test_session_failure fixture
injects these failures offline; hardware tests do not deliberately crash a device.
It also checks single-object reuse across changed bindings, reset ordering,
recoverable append/reset errors, and exactly-once cleanup.

## Minimal PyTorch device backend (workspace integration)

The sibling workspace torch_intel_npu.py and npunlock-probe/torch-device/backend.cpp
register intel_npu:0 using PrivateUse1. A C++ c10 allocator creates owned Level Zero
shared buffers; TensorImpl and Storage both have the actual device dispatch/type.
Storage deleters retain buffers until the last view is gone. The Python adapter
reuses the validated NPU4000 compiler and same-context child graph sessions.
The C++ allocator now retains exact-size unused buffers, up to 16 MiB and 64
blocks. Recycling happens only after the last Storage reference disappears;
live outputs and KV snapshots never become scratch buffers. Allocation count
still means logical Tensor allocations; driver_allocations/allocation_reuses
and cached_buffer_bytes/blocks report physical reuse and unused reservations.
torch.intel_npu.empty_cache() releases unused blocks without touching live
Storage or graphs. Shutdown drains the cache; failed contexts also quarantine
cached allocations. This cache applies to C++ Tensor storage, not the low-level
NativeLibraries.create_buffer API. torch.empty contents remain unspecified.
No Tensor subclass or CPU-storage device-property override is used.

CPU .to("intel_npu"), .cpu(), same-shape FP16/FP32 copy_, clone, contiguous factories,
view/as_strided metadata and add/sub/mul/div/neg/abs/sign (including out=) are
implemented for FP16/FP32, rank 0-4 and 1-1048576 elements, with <=65536-element
custom compute tiles (see the large-tensor extension below). Arithmetic binds the
existing allocation directly; no host payload staging occurs between operations.
Kernel bindings require contiguous offset-zero tensors covering the allocation.
Unsupported operations reject instead of falling back to CPU arithmetic.

Device .half()/.float()/.to(dtype) and sum/mean now keep intermediate payloads
in Level Zero allocations. The FP32-to-FP16 SHAVE kernel writes binary16 codes
in uint32 lanes; a metadata view and verified DMA-only StridedSlice compact
these into an ordinary FP16 output. No host unpacking is used in this backend.
All 65536 half encodings and 8192 random FP32 cast inputs were checked.

ReduceSum/ReduceMean carriers use custom sequential FP32 accumulation and the
existing subnormal-safe add32/div32 helpers. Native reduction kernels were
observed to flush FP32 subnormals. Reduction code fingerprints, dense CMX
layouts, non-aliasing and full reduction extent per invocation are validated;
partial reductions are rejected. Scalar/singleton reductions reuse Abs's ABI.
sum/mean support dimension lists, negative axes, keepdim, FP16/FP32 dtype and
exact-shape out=. sum converts its inputs to the output dtype; FP32-input mean
keeps FP32 accumulation even with FP16 output, matching tested Torch behavior.
FP16 reductions accumulate in FP32 before output conversion; CPU reduction
order/partial-result rounding can differ. Parallel trees are not implemented.

Broadcasting and scalar arithmetic now materialize operands with DMA-only
Broadcast graphs. FP32 values are replicated as pairs of 16-bit storage words,
preserving bits without numeric FP16 conversion. The internal transport may
have rank 5; public tensors have rank <=4 and <=1048576 elements. Mixed
FP16/FP32 arithmetic follows Torch result-type rules. Right-side scalar FP16
mul/div use FP32 opmath, unlike add/sub's input rounding, matching the current
CPU reference. Python real scalars and real CPU 0D tensors are cached in up to
128 owned NPU allocations; warm reuse needs no uploads. Shutdown frees them.
CPU non-scalar operands, bool subtraction, alpha !=1 and division rounding
modes other than None reject.

Two-dimensional @/mm/matmul (including exact-shape out=) broadcast A(M,K,1)
and B(1,K,N) into resident (M,K,N) products, use SHAVE FP32 multiplication and
reduce axis K, then cast FP16 output if needed. Each expanded compute tile is
<=65536 elements; larger products use the M/N tiling described below. Inputs
may be contiguous or complete dense permutations, with matching dtype. No host intermediate payload
copies, DPU MatMul or fused multiply-add are used. This correctness
path materializes products within bounded tiles; it is not a demonstrated CPU/GPU
speedup. out= reuses final storage, not every intermediate allocation.

Transpose/t/permute and detach use standard PyTorch metadata views and preserve
Storage aliasing. contiguous(), copy/download and matrix/Linear inputs can
materialize complete dense permutations using DMA-only U8 Transpose graphs.
The trailing dimension holds all 2/4 bytes of each FP16/FP32 value together;
no numeric conversion is performed. Session argument sizing now accepts bounded
U8 transport (precision enum from Intel's
[graph extension header](https://github.com/intel/level-zero-npu-extensions/blob/main/ze_graph_ext.h)).
Torch arithmetic dtypes remain FP16/FP32. Offset/cropped/expanded allocations
reject; elementwise/reduction inputs still require contiguous() first.
All 65536 binary16 encodings and 65536 random binary32 encodings were checked
bit-for-bit through transpose materialization, including NaN payloads.

addmm supports bias broadcasting, real alpha/beta and exact-shape non-aliasing
out=. beta=0 ignores NaN/Inf bias. FP16 multiplies, reductions, scaling and bias
addition stay FP32 until the final cast, avoiding intermediate half overflow.
Linear/F.linear supports rank 1-4 inputs, flattening leading dimensions into M;
M*K*N per compute tile remains <=65536, with larger input/output allocations
handled by the current M/N tiling. Ordinary CPU-initialized nn.Linear modules can .to the
device, preserving parameter requires_grad metadata. Inference uses no_grad /
inference_mode; the explicit first-order training path is described below.
eval() alone does not disable gradients. Normal module transfers,
weight copy_ and load_state_dict are supported; weights are materialized afresh,
so compiled graph caching does not cache stale parameter payloads.

Batched/vector matmul, higher-order autograd,
random generation, arbitrary in-place arithmetic, streams/events, storage resize/serialization,
device compilation and GPU interoperability are not implemented in this backend.
The larger CPU-staging adapter's coverage does not imply these device features.
It remains dependent on the Intel compiler/driver, without an OpenVINO runtime.

build_torch_npu_device.ps1 uses a workspace-local MSVC/Windows SDK, and records
the extension/source/session hashes plus the Torch version in build.json.
The Python adapter rejects stale builds. shutdown closes graphs, disables new
operations, and leaves existing allocations owned by live Tensor Storage.

## Bounded first-order device training (workspace integration)

torch_npu_autograd.py registers explicit AutogradPrivateUse1 formulas using
ordinary torch.autograd.Function. Supported derivatives cover add/sub/mul/div,
sum/mean, 2D mm/matmul, addmm, Linear, small Conv2d, ReLU and matching-shape/dtype
MSELoss. Tensor payloads and gradients remain in Level Zero allocations; CPU
shape/index metadata generation is not numerical payload fallback. Higher-order
autograd rejects. Cross-device gradients from CPU requires_grad uploads, CPU
scalar tensors in differentiable arithmetic, unlisted derivative operators and
general optimizer coverage are not implemented.

NCHW Conv2d supports groups=1, non-transposed convolution, stride/padding/dilation
and optional bias. A DMA-only byte Gather/Concat with a zero sentinel builds
im2col windows. Existing FP32 matmul/reduction kernels compute forward and weight
gradients. Input gradients use the inverse gather followed by overlap reduction.
Window M*K, output M*out_channels and inverse-fold storage each stay <=1048576
elements, using the bounded DMA transport described in the large-tensor extension.
Matrix M/N tiling removes the M*K*out_channels product limit; window/fold
transport also uses bounded DMA tiles, and DPU convolution is absent. ReLU forward/backward uses four
new small bit-preserving SHAVE kernels built from resident_activation.c.

Basic torch.optim.SGD uses NPU arithmetic and a DMA write into parameter storage:
momentum=0, weight_decay=0, nesterov=False, foreach=False, fused=False and
differentiable=False. NPU-to-NPU copy_ now uses DMA instead of host memmove.
Autograd storage/version semantics and branch/leaf gradient accumulation are
checked. Tensor creation/initialization remains on CPU before upload; NPU RNG
and cross entropy, AMP and full standard ResNet coverage are absent. See the
extended BatchNorm/global-pooling training support below.

The workspace run_torch_npu.ps1 -Training executes bounded tests with synthetic
data: MLP, small Conv2d network and a TinyResNet with one two-convolution residual
block, ReLU, spatial mean and Linear head. The TinyResNet intentionally excludes
BatchNorm and is not torchvision ResNet18/50. CPU FP16 comparison disables
oneDNN on this platform so the basic CPU half backward implementation is used.
No performance advantage or ImageNet training claim is made.

The full training check passed 11 groups and 10548 NPU submissions: 102
arithmetic/matrix/convolution gradient comparisons, 65546 ReLU bit-pattern and
gradient cases, and 15 SGD steps for each network/dtype. Every training run
reduced loss with per-step CPU gradient/parameter agreement. TinyResNet loss
went 0.160034->0.016724 (FP16) and 0.296608->0.056952 (FP32). Warm steps made no
host payload copies or new graph compilations; explicit validation downloads
occur after each measured step. All buffers returned to zero after shutdown.
The updated full inference regression passed 33 groups and 19476 submissions;
offline Python checks total 41, including gather index-bound/DMA-only guards.

## Wider model training

The workspace `run_torch_npu.ps1 -Models` checks a 3152-parameter 32->64->16 MLP
with batch=64, and an 11020-parameter four-block SmallResNet with ten convolutions,
8->16 channel changes, stride-2 projection, BatchNorm, ReLU, global average
pooling and Linear. Inputs are 2x3x8x8; synthetic MSE is not a classification benchmark.
Both FP32 and FP16 Conv/Linear paths run, with FP32 BatchNorm parameters in the
half network. Standard BatchNorm2d requires track_running_stats=False because
the default INT64 batch counter is unsupported. F.batch_norm running buffers,
unbiased running variance updates and eval gradients are implemented/tested.
AdaptiveAvgPool2d currently accepts NCHW output_size=(1,1) only.

Matrix products larger than 65536 use contiguous DMA slices and permutations
to extract M/N tiles, retaining the full FP32 reduction when K<=65536.
Wider K uses bounded K slices and compensated FP32 partial-result reduction.
Output assembly uses byte DMA Concat and is
hierarchical above 63 inputs to respect the native 64-argument graph bound.
Individual input/output allocations contain at most 1048576 elements.
The rsqrt-f32 SHAVE kernel normalizes subnormals and uses integer square root
plus FP32 reciprocal; sqrt is rounded to nearest, reciprocal adds a rounding.

FP32 model trajectories are checked independently against CPU. Deep FP16
SmallResNet rebases the CPU reference onto actual NPU weights before each step,
outside the measured step. The original step-5 failure was traced to three half
convolution rounding differences that eventually changed one residual ReLU mask.
An intervention suppressing that entry reduced the stem-gradient relative L2
error from 6.25% to 0.53%. FP32 Neumaier compensation in resident sum/mean removed
the mask difference at the captured checkpoint and reduced the error to 0.174%.
All 15 steps now pass the original pointwise gradient/update tolerances, without
relaxation. Near convergence, relative gradient error can still reach 22.6%; the
absolute tolerance is insufficient to certify small relative errors near zero.
An additional 1024x static loss-scaling experiment did not eliminate late errors.
The report remains passed_with_limitations: independent FP16 trajectories and
bitwise CPU parity are not certified. FP32 is recommended for strict deep-model
CPU comparisons. Validation downloads never compute the NPU payloads.

On this driver, graph destruction/reimport around LRU eviction reproducibly
caused device-lost failures in the wider checks. U8 broadcast did not resolve
them; lowering cache capacity moved the failure earlier. Retaining graphs
avoided these failures in the checked workloads. The workspace backend now
retains up to 512 graphs until shutdown and rejects new shapes at capacity;
the underlying driver cause is unconfirmed. No automatic retry or use of a
failed context is allowed. This is a bounded workaround, not a driver fix.

The extended run made 31938 submissions across nine groups, with 79
matrix/convolution/BatchNorm/pooling comparisons and 8203 rsqrt bit patterns.
Both wide MLPs and FP32 SmallResNet passed 15-step strict CPU gradient/update
comparisons. With compensated accumulation, FP32 residual loss fell
0.239699->1.75163e-7; half residual loss fell 0.258057->2.74181e-6. All 15
same-weight half gradient/update comparisons pass the unchanged pointwise
tolerance, but relative L2 error reaches 22.6% (minimum cosine 0.97406).
All four runs used zero warm-step host payload copies/new compilations,
excluding explicit verification copies. All tensor allocations were freed
on shutdown, and the context remained healthy. The report is retained as
torch-npu-models-compensated-1.json in the workspace research/results; the original
failure reports and checkpoint are retained. Detailed diagnostics are in the
workspace research/FP16_TRAINING_DIAGNOSIS.md. Six dedicated compensated-reduction
regressions check cancellation, FP16/FP32 GEMM, Inf/NaN and FP32 subnormals.
The original 11-group training regression passed 10548 submissions; the full
33-group inference regression passed 19476 submissions, both with clean tensor
shutdown and healthy contexts. Offline Python checks total 42. Six byte-Concat
hardware profiles passed, including 63 inputs plus one output.

SAU.ABS.f32 also flushes subnormals. The FP32 Abs kernel now clears the sign bit
using integer load/AND/store, with regression checks in both execution paths.

## Large resident tensor extension

The current workspace intel_npu allocator supports up to 1048576 numeric elements
(4 MiB FP32 / 2 MiB FP16). MAX_ELEMENTS=65536 remains the custom SHAVE task bound.
Elementwise operations/casts use exact byte DMA slices, bounded computation and
DMA concatenation. Large reductions permute non-reduced/reduced dimensions into
a matrix and tile output rows; widths above 65536 use compensated FP32 partial
sums and a second sum. Means divide by the full reduction width once. This
reassociates sums and does not certify bitwise parity with CPU or the old order.

GEMM tiles M/N and, for K>65536, K. Columns use DMA permutation
and contiguous slices; a large column Gather caused device-lost on this driver.
K partials stay FP32 and use compensated reduction before final conversion;
this reassociates dot products. Small convolution window/fold allocations may
contain up to 1048576 elements. Their
transport uses source spans <=65536 and Gather outputs <=8192, followed by byte
Concat. Larger Gather carriers either lost the device or introduced compute
tasks rejected by DMA-only validation. Failure logs are retained; the low-level
Gather bounds and precision/transport checks are not relaxed.

`run_torch_npu.ps1 -Large` checks million-element arithmetic/reductions/casts,
bit-preserving copies/permutations, differentiable broadcast/casts, FP16/FP32
Linear training with 131072-element weights or 65552-element activations, and
FP32 Conv2d/BatchNorm/global-pool training at 2x3x65x65. The convolution output
has 67600 elements and window/fold storage has 228150. Three steps reduced loss
0.189275 to 0.147612 with original CPU gradient/input-gradient/update checks.
Warm steps have zero measured host payload copies/new compilations; verification
downloads are excluded. Cases use separate processes for the bounded graph cache.
All ten large-tensor groups passed with 7263 submissions and healthy, allocation-free
shutdowns. Original device/training regressions passed 33/11 groups (19476/10548
submissions); mixed training passed its 15+5-step checks, retaining the known FP16
baseline limitations in the overall report. Offline validation passed 43 checks.

The CPU-staging and old fixed-shape session adapters retain their old 65536
limit. Storage growth is not a throughput improvement or access to the whole
shared-memory budget. Rank<=4, per-Tensor allocation, compiler layout constraints
and 512 retained graphs still bound supported workloads.

The frontend now streams convolutions when full windows or the kernel-area fold
upper bound exceed allocation capacity. NHWC DMA transport and image-row-aligned
gathers reuse bounded static carriers. Forward saves only x/weight for autograd;
weight gradients recompute windows and combine FP32 partials with a bounded binary
tree. Input gradients gather output-gradient neighborhoods and contract against
permuted weights, avoiding a full fold allocation. FP16 compute windows use FP32
transport and arithmetic before final conversion. CPU work only generates indices.
Partial sums reassociate gradients; neither global compensation nor CPU bit parity
is claimed. `run_torch_npu.ps1 -Stream` runs bounded matrix/large-batch/streaming
convolution checks in fresh processes; `test_torch_npu_geometry.py` compares the
forward/input-gradient index geometry with CPU PyTorch, including stride/dilation.
Graph cache capacity and DMA-only validation are unchanged. A cache-capacity
failure from the initial unaligned scheme is retained in research/results.
The six stream-check processes passed ten groups with 22589 NPU submissions,
including K=1048576, batch=65537 Linear training, and FP16/FP32 convolution with
1115136-element full windows/folds replaced by bounded tiles. Forward, input/
parameter gradients and SGD updates passed the original tolerances; CPU weights
were rebased each step. Stride-2/dilation-2/no-bias and dense permutation gradients
also passed. Warm steps made zero measured explicit host tensor copies or new
compilations, and all processes shut down with healthy contexts and zero buffers.
The FP16 streaming case retains 297 graphs versus 484 before sharing FP32 DMA
carriers. These are correctness/temporary-storage checks, not throughput claims.

`compile_square_gemm(size, kernel_elf, libraries=...)` is a separate experimental
direct FP32 SHAVE path for complete row-major square matrices of size 2..64.
ReferenceSW with one tile preserves full Power inputs in one invocation; the
validated Power code window is then replaced by our compensated GEMM kernel.
The patch retains all existing profile, code-fingerprint, FP32, CMX and alias
checks and additionally rejects partial matrices or multiple invocations.
The graph's Power operation is only a carrier and does not execute after patching.
The kernel has no data section and reuses the subnormal-safe arithmetic helpers.

`run_torch_npu.ps1 -Script torch_npu_gemm_demo.py` checks 23 numerical cases,
bitwise old/new FP32 and FP16 Linear training, and interleaved resident timings.
FP16 training still casts operands to FP32 using existing NPU operations; this
is not a native FP16-input GEMM kernel. Larger squares regress in this single
SHAVE prototype. Its original results are in `research/results/gemm/REPORT.md`.

`compile_parallel_square_gemm` adds two disjoint row tasks on one tile for
sizes 2..64. Both use the existing complete B upload after validating the whole
CMX spans, DMA extents and completion dependencies. `compile_four_tile_square_gemm`
supports sizes 8/16/32/64 with input/output shapes `(4, 2, size*size/2)`:
four complete replicas, one task per tile, disjoint computed rows and zero
elsewhere. The experiment assembles C with the existing NPU sum reduction;
two NPU broadcasts, GEMM and reduction require four graph submissions total.
No remote tile CMX access or partial host allocation binding is used.

These patches retain the strict profile, code-fingerprint, FP32, CMX and alias
checks. They additionally validate full byte-copy DMA widths, IO relocations,
queue links and SHAVE barriers. Only the code window and proven DMA ordering
bits may change; layouts, extents, addresses and barriers remain intact.
The fast kernels inline the original normal FP32 predicates and outline rare
IEEE/subnormal handling, with `-ffp-contract=off` and unchanged compensated K order.
Run `run_torch_npu.ps1 -Script torch_npu_gemm_demo.py -ScriptArguments '--parallel'`
for the expanded numerical, training and interleaved timing experiment. Smaller
sizes favor one tile; four tiles improve 64x64 over the expanded-product path,
but 32x32 still regresses. At that stage the normal ATen matrix path was unchanged;
rectangular kernels were added in the following stage; native FP16 input remains future work. See
`research/results/gemm-parallel/REPORT.md` records that stage.

`compile_rect_gemm((M,K,N), kernel_elf, libraries=..., replicas=4)` extends the same full
four-tile DMA proof to 64-aligned packed capacities up to 16384 floats per
replica. Its physical input/output shape is `(4,2,capacity/2)` for four tasks,
or `(8,8,capacity/8)` for eight tasks (two per tile). Each task has complete A/B/C;
eight-task DMA copies two adjacent full replicas per tile in one descriptor.
Input A begins
with four exact FP32 scalar arguments `[12345,M,K,N]`, followed by row-major A;
input B starts with row-major B. Both are zero-padded on the NPU. The kernel
checks finite integer dimensions, M/N<=64, K<=256 and all three extents against
the capacity before accessing data. It zeroes each full partial-C buffer and
computes disjoint rows with the existing FP32/Neumaier helpers.

`torch_npu_rect_gemm.matrix_fp32` tiles M/N<=256, preserving the full K<=256
order. For K=256 it uses at most 63 A rows to leave room for the header.
All slices, padding, replication, output selection and assembly
run on the NPU using existing whole-allocation operations. The current matrix
function defaults to eight replicas and caches packed inputs only within one
call, so subsequent SGD updates cannot reuse stale weights. Four replicas are
still selectable explicitly. Output DMA selects the producing row directly,
without reducing the full partial buffers. For eight replicas, whole-allocation
DMA transposes and trims the partial buffer to <=32768 useful elements before
Gather; its source ceiling stays 65536 and each selected output is <=4096.
Initial host copies
are cached scalar shape/zero arguments only; warm execution makes no measured
host payload copies or compilations. Shape-specific calls reuse graph sessions
by packed capacity; their runtime header supplies the current dimensions.

Only measured 128x128x128 and 256x256x256 cases select this path through normal
Torch matrix APIs by default. The original expanded-product implementation is
retained as `_matrix_fp32_expanded`; other shapes keep it. FP16 still uses FP32
opmath with one final conversion. 38 numerical/API checks and three FP32/FP16
training configurations pass with eight tasks, including tiled non-square gradients
and normal 128x128 Linear dispatch. Offline Python validation has 48 checks,
including rejection of partial eight-task inputs and invalid dependencies.
The original four-task stage is recorded in `research/results/gemm-rect/REPORT.md`;
the eight-task packing/selection optimization and interleaved timing are in
`research/results/gemm-eight/REPORT.md`. Native FP16, K>256 in this direct kernel,
broader default shape dispatch and GPU interop remain unsupported.

## Explicit weight-only INT4 / NF4 DPU inference

The symbolic layer now serializes `i4/u4/nf4` types and provides
`constant_packed(bytes, shape=..., dtype=...)`: two codes per byte, low nibble
first, exact ceil(elements/2) bytes, and zero unused high bits for odd counts.
This does not add integer device allocations or lowbit Program.run IO.

Workspace `torch_npu_lowbit.QuantizedLinear.from_float(cpu_linear, format='nf4')`
prepares immutable packed INT4/NF4 weights and FP16 scales on CPU. Runtime
requires 2D intel_npu FP16 activations and returns FP16. A direct driver IR
graph converts compressed constants, applies scales, reshapes and executes
MatMul/bias on DPU. Compilation requires the validated 8086:643e / compiler8.3
profile and nonempty DPU sections. It is independent of the true FP32 carrier
contract and adds no OpenVINO runtime dependency. Warm calls reuse the weight/
shape graph and do not reserialize/hash full weights.

Per-output-channel scaling is the default; group sizes must divide K.
The 8.3 grouped signed INT4 small-M route has reproduced large numerical
errors, also with one or two tiles. The wrapper conservatively pads grouped
INT4 M<32 to 32 with device DMA, then trims the result; padding, MatMul and trim
are now compiled into a single graph submission. Extra storage
must still fit the allocation bound. This is a tested workaround, not a fix
to the compiler itself. NF4 needs no such padding in the checked cases.

Twenty numerical checks, two quantized ReLU MLPs, activation/autograd guards,
eight interleaved timing configurations and 33 original device regressions
pass. Offline validation has 49 npunlock checks plus three codec/IR checks.
Large DPU results can differ from a separately rounded FP16-weight graph;
independent FP64 scaled-code references show <0.03% relative L2 error in the
measured cases, with an additional weight-rounding error check. This does not
extend the exact FP32/subnormal guarantee to DPU execution.

Per-channel 1024x1024 graphs have 540672 constant bytes versus 1872896–2031616
for matched decoded FP16 graphs. Group-128 graphs can expand to approximately
the same constant footprint as FP16. Lowbit storage alone does not certify
lower runtime memory or faster execution. See `research/results/lowbit/REPORT.md`.
The optional `compact_groups=True` mode emits one compressed MatMul per group
and a balanced FP16 addition tree, with at most 32 groups. It avoids the
multi-axis grouped lowering path; tested 1024x1024 group128 constants occupy
655360 bytes instead of approximately 1.9–2.0 MiB. It is disabled by default:
FP16 partial rounding changes results, and overflowing partials have reproduced
DPU clipping with incorrect cancellation even when the full dot product is
finite. Validate partial ranges and model quality before using this experiment.
Current checks include 42 old/default/compact Linear comparisons, two compact
MLPs, six exact grouped code tests, two zero tests and two documented clipping
counterexamples. See `research/results/lowbit-group/REPORT.md` for same-process
timings, bounds checks and source provenance. No runtime dependencies were added.
The module supports frozen inference only: no lowbit autograd, QLoRA, ordinary
state_dict weight persistence, checkpoint-layout import or general lowbit ATen.

The workspace wrapper also accepts `format='int8'`: signed bytes with FP16
